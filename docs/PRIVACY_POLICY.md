## 11. End-to-End Encryption

**End-to-End Encryption (E2E)** is a core feature of SXWer AI ChatBot. This means that **only you and your device** can read your messages - not even we can access them.

### **🔐 How E2E Encryption Works**

```
1. Your Device
   ├─ Generates X25519 key pair (private key NEVER leaves device)
   └─ Sends public key to server

2. Server
   ├─ Receives your public key
   ├─ Sends its own public key to you
   └─ Both sides compute shared secret (NEVER transmitted)

3. Message Flow
   ├─ You: Encrypt message with shared secret + nonce
   ├─ Server: Receives ciphertext only (cannot read)
   ├─ Server: Processes request, encrypts response
   └─ You: Decrypt response with shared secret
```

### **📋 What E2E Encryption Protects**

| Data | Protected? | Notes |
|------|------------|-------|
| **Chat Messages** | ✅ Yes | Encrypted before leaving device |
| **AI Prompts** | ✅ Yes | Encrypted if AI assistance enabled |
| **AI Responses** | ✅ Yes | Encrypted before leaving server |
| **Session IDs** | ⚠️ Partial | Anonymous, but not encrypted |
| **Consent State** | ⚠️ Partial | Minimal data, but not encrypted |
| **Public Keys** | ❌ No | Needed for key exchange (but contain no PII) |

### **⚠️ Limitations of E2E Encryption**

E2E encryption **does not** protect against:
- **Compromised Device:** If your device is compromised, an attacker can read decrypted messages
- **Browser Extensions:** Malicious extensions with page access can intercept messages
- **Screen Capture:** Someone looking at your screen can see messages
- **Keyloggers:** Malware on your device can capture messages before encryption
- **Legal Compulsion:** If we are legally compelled to modify our server, E2E may be bypassed

### **🔑 Key Management**

#### **Key Generation**
- **When:** On first use, or when you rotate keys
- **Where:** In your browser (using Web Crypto API)
- **How:** Cryptographically secure random number generation

#### **Key Storage**
- **Private Key:** Browser memory only (lost on tab close)
- **Public Key:** sessionStorage (cleared on tab close)
- **Shared Secret:** Computed locally, never stored

#### **Key Rotation**
You can rotate your keys at any time from the **Encryption Status** page:
1. Generate new key pair
2. Old private key is zeroed in memory
3. Server clears old public key registration
4. Old messages become unreadable

#### **Key Export/Import**
You can export your keys as an **encrypted backup**:
- **Encryption:** PBKDF2 (310,000 iterations, SHA-256) + AES-GCM (256-bit)
- **Format:** Encrypted JSON file
- **Security:** You must provide a password to decrypt

## 17. Blockchain and Consent Ledger

### **🔗 Optional Blockchain Consent Ledger**

We offer an **optional, opt-in** blockchain-based consent ledger for users who want a **tamper-evident audit trail** of their consent decisions.

### **✅ What the Blockchain Stores**

**Only** the following **non-identifiable** data is stored on-chain:

| Field | Description | Example |
|-------|-------------|---------|
| `eventType` | Type of consent event | `CONSENT_GRANTED`, `CONSENT_REVOKED` |
| `documentHash` | SHA-256 hash of consent document | `a3f8c7...` |
| `receiptHash` | SHA-256 hash of receipt object | `b4e9d2...` |
| `timestamp` | Unix milliseconds | `1717234567890` |
| `policyVersion` | Version of policy accepted | `1.0.0` |
| `schemaVersion` | Receipt schema version | `1.0` |
| `appVersion` | Application version | `1.2.3` |
| `nonce` | Replay protection value | `c5d1e8...` |
| `walletId` | Optional pseudonymous identifier | `0x123...` (if connected) |
| `signature` | Optional digital signature | `d6e4f1...` (if signed) |

### **❌ What the Blockchain NEVER Stores**

The blockchain **never** stores:
- Conversation history
- Messages, prompts, or AI responses
- Usernames, real names, or any PII
- Photos, images, or videos
- Voice recordings or audio
- Safety plans or health information
- Legal records
- Location data
- Device fingerprints
- IP addresses
- **Any personally identifiable information**

### **🔒 Why Blockchain Does Not Store Chat Messages**

Chat messages are **personal, sensitive**, and often contain information that could **harm users if disclosed**. Blockchain ledgers are:
- **Permanent:** Once data is written, it **cannot be deleted**
- **Public:** Anyone can read the blockchain
- **Immutable:** Data cannot be modified or removed

Storing message hashes would allow **correlation attacks**: an adversary with access to the original message could verify whether it was sent, when, and by whom. This **violates our privacy model**.

The blockchain exists **only** as a **verification ledger** for consent and policy decisions - **not** as a conversation store.

### **⚖️ Human Rights by Design**

Every blockchain feature must answer **YES** to all eight questions:

1. ✅ **Can the user understand what is happening?** - Every event is shown in plain language
2. ✅ **Can the user meaningfully consent?** - Full disclosure is shown before activation
3. ✅ **Can the user refuse?** - Blockchain is **always optional**; the App works without it
4. ✅ **Can they revoke consent?** - "Revoke Consent" button writes an immutable revocation receipt
5. ✅ **Can they inspect their data?** - Consent Ledger page shows every record
6. ✅ **Can they export it?** - "Export Consent" downloads a portable JSON file
7. ✅ **Can they delete local data?** - "Disable Blockchain" clears the local ledger
8. ✅ **Can they continue without blockchain?** - Local-first is **always** the default

### **🔗 Blockchain Providers**

We support multiple blockchain providers. You can choose:
- **Mock/In-Memory:** For testing (default, no real blockchain)
- **Ethereum:** Decentralized, public blockchain
- **Polygon:** Ethereum-compatible, lower fees
- **Hyperledger Fabric:** Permissioned, enterprise blockchain
- **Hedera Hashgraph:** Fast, efficient consensus
- **Consortium Chain:** Custom, private blockchain

**Default:** Mock/In-Memory (no real blockchain, no data leaves your device)

### **🛡️ Blockchain Privacy Architecture**

```
Client (Your Device)
  ├─ Consent Manager (consent_manager.js)
  │   └─ Only stores consent state in memory
  ├─ Local Encrypted Storage (IndexedDB / in-memory)
  │   └─ Session data, automatically deleted after 24 hours
  └─ Optional Blockchain Ledger (services/blockchain/consentLedger.js)
      ├─ Only writes SHA-256 hashes to blockchain
      └─ Never writes raw data or PII
          
Server
  └─ Only sees ciphertext (encrypted data)
      └─ Cannot read messages or consent documents

Blockchain
  └─ Only stores hashes and metadata
      └─ No PII, no messages, no identifiable data
```

### **🔄 Consent Lifecycle**

```
1. User opens App (blockchain disabled by default)
2. User navigates to Consent Ledger page
3. Full disclosure is displayed
4. User clicks "I understand - Enable Blockchain"
5. CONSENT_GRANTED receipt created and submitted
6. User uses the App normally
7. User can revoke at any time → CONSENT_REVOKED receipt written
8. User can export ledger history at any time
9. User can disable blockchain → local ledger cleared, wallet disconnected
```

### **🗑️ Data Lifecycle**

| Data | Storage | Deletable? | Notes |
|------|---------|------------|-------|
| Consent receipts (local) | In-memory (session) | ✅ Yes | "Disable Blockchain" button |
| On-chain consent receipts | Blockchain | ❌ No | Immutable by design (contains no PII) |
| Conversation history | Local only | ✅ Yes | "Delete my data" button |
| Safety plans | Local only | ✅ Yes | "Delete my data" button |
| Settings | Local only | ✅ Yes | "Delete my data" button |

## 19. Data Breach Notification

### **🚨 What Constitutes a Data Breach?**

A **personal data breach** means a breach of security leading to the **accidental or unlawful destruction, loss, alteration, unauthorized disclosure of, or access to** personal data.

### **⏰ Notification Timeline**

| Timeframe | Action |
|----------|--------|
| **Within 72 hours** | Notify supervisory authority (if high risk) |
| **Without undue delay** | Notify affected users (if high risk) |
| **Immediately** | Contain and investigate the breach |

### **📋 Breach Notification Procedure**

1. **Detection:** Automated monitoring or user report
2. **Assessment:** Determine scope, impact, and risk level
3. **Containment:** Isolate affected systems
4. **Investigation:** Identify cause and extent
5. **Remediation:** Fix the vulnerability
6. **Notification:**
   - Supervisory authority (within 72 hours if high risk)
   - Affected users (without undue delay if high risk)
7. **Documentation:** Record all details for audit
8. **Prevention:** Implement measures to prevent recurrence

### **📊 Risk Assessment**

We assess breaches based on:
- **Nature of data:** What type of data was affected?
- **Scope:** How many users were affected?
- **Impact:** What is the potential harm to users?
- **Likelihood:** What is the likelihood of harm occurring?

**Risk Levels:**
- **Low Risk:** No notification required
- **Medium Risk:** Notify supervisory authority
- **High Risk:** Notify supervisory authority **and** affected users

### **🔒 Breach Prevention Measures**

We implement the following to **prevent** data breaches:
- End-to-end encryption
- Data minimization
- Regular security audits
- Penetration testing
- Employee training
- Access controls
- Audit logging
